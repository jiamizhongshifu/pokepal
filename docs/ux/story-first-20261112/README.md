## 1. 产品结论

将产品主线改为：**宝宝作为小训练师，与宝可梦一起经历一个个能看懂、能感受到的生活故事。** 爱、习惯、品德和英语通过角色的处境、动作与回应发生。收集伙伴继续提供探索动力。

用户希望：“通过故事让他们能够感受到生活里的爱与感动。”

保留核心循环：**完成任务 → 获得积分 → 兑换精灵球 → 捕捉喜欢的宝可梦 → 一起生活。** 任务的主要形态变成故事中的共同经历；喂食、种植、游戏成为有前因与结果的动画场景。故事里可以参与，也可以安心看完。

本轮重点是重新组织体验和内容制作。当前源码已经使用 PokéAPI；更换数据源不能解决按钮多、场景割裂与故事演绎不足的问题。

### 产品目标与边界

| 目标 | 设计约束 |
|---|---|
| 开始一次体验不需要理解功能菜单 | 一个显著的开始入口，自动续接上次故事或推荐一集 |
| 看到行动就理解意思 | 关键行为必须展示准备、行动、结果，不能只移动角色立绘 |
| 愿意参与，仍有自己的决定 | 故事内最多 0–2 个可选参与点；保留选喜欢的伙伴、暂停、离开 |
| 英语自然出现 | 每集 1 个主要表达、1–2 个熟悉词；语言与正在发生的动作对齐 |
| 收集循环可靠 | 余额、库存、收藏保留；奖励、兑换、捕捉都有持久化与重复操作保护 |
| 温柔地结束 | 不自动连播下一集；到时休息，不用缺球或未完成剧情要求孩子继续 |

本轮不扩展对战、排行榜、强制口语评分、儿童自由 AI 聊天、移动端打包。动态故事、语言理解、生活习惯的实际效果都要通过样片和家庭观察验证。

## 2. PokéAPI 的作用与现有接入

### 它是什么

[PokeAPI/pokeapi](https://github.com/PokeAPI/pokeapi) 是宝可梦资料服务的源码，使用 Python / Django，提供 REST API，并支持 GraphQL。它不是现成的游戏前端或儿童内容引擎。数据主要从 CSV 构建，图片和叫声由独立资源仓库维护。

| 能力 | 对本产品的用途 | 边界 |
|---|---|---|
| `pokemon`、`pokemon-species` | ID、多语言名称、类型、颜色、身高体重、形态 | 不需要把战斗数值变成宝宝必须理解的系统 |
| `evolution-chain` | 收藏、进化关系 | 原作捕获率不应覆盖现有“投球必定成功”规则 |
| official-artwork、HOME、dream-world 等图片 | 图鉴、角色外形参考、收藏缩略图 | 通常是单角色图，不是完整绘本场景 |
| Showdown / 部分世代动态 sprite | 图鉴小动画、轻量过渡 | 没有连续的洗苹果、喂食、浇水、拥抱等生活剧情 |
| `cries.latest/legacy` | 宝可梦叫声 | 不是中英旁白或角色对白 |

以上依据：[API 文档](https://pokeapi.co/docs/v2)、[sprites 仓库](https://github.com/PokeAPI/sprites)、[cries 仓库](https://github.com/PokeAPI/cries)。公开资源结构中没有可直接承担本项目生活叙事的 3D 骨骼与动作控制器；也没有现成的故事、课程、存档和奖励系统。

官方 REST 文档说明接口只读、无鉴权，当前没有固定限流，但要求缓存结果、减少请求。建议继续在制作阶段同步，儿童运行时读本地或现有静态资源服务。无需自建整套 PokéAPI，也无需下载超过 10 GB 的完整 sprites 子模块。[使用政策](https://pokeapi.co/docs/v2#fairuse)、[资源部署说明](https://github.com/PokeAPI/pokeapi#setup)。

代码许可证为 BSD-3-Clause；图片仓库另有版权说明。开源代码许可不能视为宝可梦角色和商标的全面授权。沿用项目 [OPEN_SOURCE.md](../../../OPEN_SOURCE.md) 对源码与第三方媒体的区分。[代码许可证](https://github.com/PokeAPI/pokeapi/blob/master/LICENSE.md)、[图片说明](https://github.com/PokeAPI/sprites/blob/master/LICENCE.txt)。

### 我们已经具备什么

- [scripts/sync-pokemon-data.py](../../../scripts/sync-pokemon-data.py) 第 20–54 行已缓存 Pokémon、species、进化链，下载官方立绘、HOME 图片和叫声；[src/data/pokemon.ts](../../../src/data/pokemon.ts) 第 18–20 行使用本地资源。
- 当前角色表为 388 条，`public/pokemon/art`、`home`、`cry` 各有 388 个文件。本轮只核对数量，没有逐个验证画面与声音。
- 现有按属性分配爱好、按颜色分配食物的逻辑是产品自编模板，不是 PokéAPI 的性格事实。新故事应另设人物小传和关系设定。
- 同步脚本遇到已有角色会提前返回，不能假定重跑就会修复全部缺失媒体。未来制作流水线需要显式的缺失检查与修复入口，本轮没有修改。
- 本轮查阅文档成功；直接请求 `pokemon/25` 时返回 403。因此没有完成当前环境的实时接口连通验收，也没有给儿童主线增加在线依赖。

结论：PokéAPI 继续负责“是谁、长什么样、资料是什么”；原创内容负责“发生了什么、为什么在意、怎样一起解决”。

[OpenAI 2026-11-04 发布说明](https://openai.com/index/introducing-images-2-6/)确认 Images 2.6 支持动态图创作，并提供 Sunburst / Flare。当前 [Images API 参考](https://developers.openai.com/api/reference/resources/images/methods/generate)包含 `output_format=gif`、`frame_count`（2–16 帧）与 `frame_duration_ms`，GIF 能力还取决于所选模型的预览访问权限。

**适合的制作单位是短动作和短镜头。** 连续三分钟故事仍需要分镜、旁白、动作衔接和播放器编排。当前会话的内置生图工具没有显式模型或 GIF 参数，不能把工具存在直接当作指定 2.6 GIF 路线已跑通。制作前以一次短样片核验实际模型、输出和一致性；如果只能得到静态帧，可用 2.6 逐姿态出图后确定性合成，不把静态图平移当作完整角色演技。

## 5. 新的核心体验

```mermaid
flowchart LR
  A[今天的相遇／接着上次] --> B[连续动态故事]
  B --> C[可选：点场景帮一下]
  B --> D[角色自然继续]
  C --> E[完整收尾与任务积分]
  D --> E
  E --> F[宝宝决定是否兑换精灵球]
  F --> G[挑喜欢的宝可梦并投球]
  G --> H[新伙伴来到小岛]
  E --> I[休息／自由陪伴]
  H --> I
```

### 首页与导航

首页是一幅有生活气息的岛屿画面。伙伴朝宝宝招手，主要邀请是“今天，一起去准备野餐吧”。点击画面中的一个大入口后开始故事，并完成浏览器声音解锁。

儿童端保留三个清晰目的：**今天的故事、我的伙伴、找新伙伴**。当页只有一个突出的主动作；其余入口保持固定图形和位置。暂停、回家、声音状态可以找到，不用长按或隐藏手势承载必要操作。家长设置继续使用成人入口。

故事屋成为可重看的回忆书；学习记录、语言设置、加练、装扮等放到合适的次级位置。现有功能逐步迁移，而不是同时展示所有入口。

### 各功能如何改变

| 功能 | 新体验 | 保留的自主决定 |
|---|---|---|
| 喂食 | 伙伴看见点心、表达需要；宝宝可点食物递过去；镜头展示接过、咬一口、吃饱 | 可以不喂、停止；已经吃饱不会被继续劝食 |
| 玩球 | 球从伙伴身边滚到宝宝面前；可点球滚回，听到 `Your turn` | 可以多玩一次或离开，不必先选小游戏与地点 |
| 种植 | 一段故事种下、照顾；之后在新的相遇里看到变化 | 可点水壶帮忙；不要求反复点击或定时上线 |
| 英语学习 | 角色需要帮助时说 `Help, please!`；物品递到面前时说 `Here you are` | 自愿跟说、重听；无需回答正确才能继续 |
| 任务 | 今天共同经历的小事情，由故事带入和收尾 | 可暂停，下次接着完成 |
| 积分兑换 | 故事结束就地显示余额与“5 积分换 1 球”的图形关系 | 兑换有明确意图，不自动花费积分 |
| 捕捉 | 看到想要的伙伴，选中它，轻点球完成投球动画 | 对象由宝宝决定，保留现有心愿与完整收藏范围 |
| 陪伴 | 已拥有伙伴在短动画中招手、坐下、玩耍，形成反复相见的记忆 | 随时回到喜欢的伙伴，不把新故事作为唯一入口 |
| 日记 | 自动保存本次共同经历的简短回忆；说给家长听是自愿的 | 不默认打开麦克风、上传录音或要求描述 |
| 家长反馈 | 看过什么、听过哪些表达、主动参与过什么 | 现实生活观察由家长记录，与系统播放记录分开 |

种植的跨天叙事不能把现实植物表现成瞬间长成。现有游戏作物浇水后 45 秒成熟；新故事若写“过了几天”，必须明确是故事时间。若操作真实农田库存，就按农田实际状态播放对应镜头；若只是故事中的菜园，不扣真实库存或伪造收获。

### 交互规则

1. **一次启动后可以不再点击，仍听完故事。** 一集最多 0–2 个可选场景动作，开始、暂停和收集选择不计入这个数量。
2. 直接点物体，不先打开功能表。可选手势采用轻点，拖拽不是唯一方法；触控目标尺寸先以至少 64 CSS px 作为样板目标，随后实际检验。
3. 一次温和邀请后，如果没有响应，角色自然继续。初步等待预算 6–8 秒，随后按试播调整；不倒计时、不反复催促，不记录为答错。宝宝按下暂停时绝不自动继续。
4. 点击必须改变此刻动作或得到明确回应，例如宝宝点水壶后，伙伴扶住水壶倒水。若剧情固定且点击无任何可见作用，就删除这个点击。
5. 只看路线与主动参与路线有同等故事内容和任务积分；不会把未发生的操作说成“你已经洗好苹果了”。角色可以说“我们准备好啦”，记录仍区分自动和主动。
6. 不把所有选择删掉。喜欢谁、还想不想玩、要不要花积分、何时离开，都是值得保留的决定。

## 6. 情感、生活习惯和英语如何进入故事

每集组织为：**一个具体愿望 → 一个小困难 → 感受被看见 → 一次行动或修补 → 关系发生温暖的变化。** 让善意落在递来的一块毛巾、留出的一个座位、耐心停下的一颗球上。

- 爱与感动：被记得、被等待、有人愿意陪伴，不用牺牲或危机煽情。
- 生活习惯：让宝宝看到为何洗净、如何收拾、累了怎样休息；不以“乖”或“好孩子”作评分。
- 品德：故事角色可以拒绝、犯错、求助和修补。友谊不因没说对一句话而消失。
- 英语：中文帮助进入情境，短英文出现在动作与需要最清楚的时刻，随后在另一场景自然再遇见。默认不逐句重复长篇中英文，也不弹词卡打断情绪。
- 一个词或句子“听过”不等于“理解”或“掌握”。保留现有学习证据分层；家长主动开启的独立练习继续单独记录。

首批主题建议：

| 小故事 | 主要体验 | 生活行动 | 主要英文 |
|---|---|---|---|
| 留给你的一颗苹果 | 我被朋友惦记着 | 共同洗净点心 | `apple` / `Thank you!` |
| 小水壶，一起提 | 求助会被听见 | 照顾植物 | `Help, please!` |
| 小球在等你 | 轮流是看得见的约定 | 来回滚球 | `Your turn.` |
| 玩具也要回家 | 一起整理更轻松 | 收拾玩具 | `Let's tidy up.` |
| 树下留一个座位 | 陪伴也可以很安静 | 休息与边界 | `I need a rest.` |
| 小小的修补 | 做错之后仍能被接纳 | 修复打翻的花盆 | `I'm sorry.` |

这是内容排期建议，不是本轮新增的已实现内容。先完成第一集，再根据制作与试用反馈决定后续规模。

## 7. 首个完整样板：《留给你的一颗苹果》

固定出演皮卡丘与伊布；宝宝以小训练师的视点来果园做客。演员是故事中的岛上朋友，未捕捉时不把它们显示成宝宝已经拥有的伙伴。首集不需要宝宝先选择演员。

主旨：**这里有你的座位，也有特意留给你的苹果。**

长度预算约 3 分 20 秒；不是必须凑满的时长。下表是 8 个叙事段落，每段由若干短动作镜头、适当停留和环境循环组成，不表示一条 GIF 连续表演 20–30 秒。中英正式台词与节奏须在样片时审阅，不用长循环填时间。核心英语为 `apple` 和 `Thank you!`，`Water`、`Help, please!` 只作为自然出现的辅助表达。

| 时间预算 | 镜头与动作 | 口播方向 | 参与 |
|---|---|---|---|
| 0:00–0:20 | 果园推近，皮卡丘铺好三个座位，伊布提来三颗苹果 | “小训练师，你来啦。今天一起吃苹果。”`Apple!` | 无 |
| 0:20–0:45 | 伊布鼻尖碰到叶子；皮卡丘指向苹果上的泥点和水盆 | “还带着一点泥，先洗一洗。” | 无 |
| 0:45–1:15 | 伊布提水壶有些吃力，停下来求助；朋友扶稳再共同倒水 | `Help, please!` “没关系，我们一起。” | 点一下水壶；未点则朋友自行协作 |
| 1:15–1:40 | 水进入盆，苹果转动，泥点洗去；小水滴碰到伊布鼻子 | “哗啦，水来了。Water。”留出环境声 | 无 |
| 1:40–2:10 | 两颗大苹果擦干；伊布用布角认真擦掉小苹果最后一滴水 | “这一颗小小的，也要擦干净。” | 点一下近处苹果；未点则伊布完成 |
| 2:10–2:35 | 小苹果放到宝宝面前的盘子里，第三个座垫被推近一点 | “这颗留给你。这里，也有你的座位。”停一拍 | 无，不要求说谢谢 |
| 2:35–3:00 | 朋友相互递点心、点头、咬一小口，安静坐下 | 角色自然说 `Thank you!` | 自愿跟说，界面无录音或评分 |
| 3:00–3:20 | 镜头拉远，三个座位仍在，树叶轻动，伙伴挥手 | “今天的野餐真好。下次见，小训练师。” | 完整结束，不自动连播 |

情绪从“被欢迎”经过“小困难得到回应”，落到“我被惦记着”。不在感动镜头上弹积分、勋章或提问。片尾短暂停顿后，再显示训练师手册中的任务结果。

这一集验证共同准备点心、可选帮忙与情境语言。它尚未验证宝宝喂已拥有伙伴、真实食物库存扣除与吃饱反馈，这些在阶段 C 的点心互动扩展中单独验收。种植、游戏分别由后续两集验证，不为了技术覆盖把所有玩法塞进同一个故事。

## 8. 奖励与收藏：保留主循环，适配故事任务

### 现行规则

每类参与每日首次 +2；课程还按主题去重；三类参与额外 +1；每日总上限 15；5 积分换 1 球；累计七个达标日赠球。故事整体是一类，因此同一天不同故事目前只奖励一次。依据：[participation.ts](../../../src/lib/participation.ts)、[pokeballs.ts](../../../src/lib/pokeballs.ts)。

### 新规则建议，尚未实施

**完整完成一集故事任务获得 5 积分，同一集每天最多一次，所有新旧来源合计仍最多 15 积分/日。** 暂停后续播、同日重播、语言版本切换和素材更新不产生重复奖励。直接跳到结尾不算完成。

选择 5 分的理由是让首次完整体验就能理解“一次共同经历 → 一颗球 → 一个新朋友”；它是产品提案，不是当前代码行为。叙事中的善意、点心和陪伴始终无条件提供，不按是否点击、跟读或选中道德答案区分所得。

| 起始状态 | 故事完成 | 宝宝主动兑换 | 捕捉成功 |
|---|---|---|---|
| 0 分、0 球 | 5 分、0 球 | 0 分、1 球 | 0 分、0 球，多一位伙伴 |
| 3 分、已有 1 球 | 8 分、1 球 | 可以不兑换，直接使用已有球 | 8 分、0 球，多一位伙伴 |
| 今日只剩 2 分奖励额度 | 本集仅加 2 分，如实显示 | 余额不足则保留，下次再说 | 不暗送球、不扣成负数 |

无球且余额足够时，兑换入口直观展示五点能量变为一颗球；已有球时可直接找伙伴。兑换必须由孩子发起，不能为了少一次点击自动花费积分。选择对象、投球是两个有意义的动作；一球仍必定成功，不增加失败和稀有度焦虑。

### 旧机制迁移与防重复

- 原余额、球库存、已捕捉伙伴、图鉴、心愿、友好度和进化记录原样保留。
- 新的每日达标条件为“完成一集故事任务，或完成原有三类参与”，同一天只累计一次；原七日进度和已发赠球记录保留。不把旧累计天数清零。
- 故事任务固定目标额度为 5 分，本身不触发旧三类 +1，也不加入旧三类计数。孩子若另行完成旧三类，仍可按旧规则获得 +1，全部走同一每日上限。界面的“三类目标”文案随迁移同步更新。
- 将“今日达标天数已累计”与“旧三类奖励已处理”拆为独立字段，例如 `dayCreditApplied` 与 `legacyCategoryBonusProcessed`，不能共用旧 `goalDone`。旧字段在迁移时映射到相应已处理状态；故事先完成只记达标日，之后旧三类仍能结算其 +1；反过来先做三类也只累计一天。达到七日后的赠球仍只发一次。这样在未触及每日上限时，新旧路径先后顺序不影响总额。
- 为每个故事设置稳定的 `taskId`，奖励键采用 `本地日期 + taskId`；画面版本和语言版本不得放进奖励身份。
- 第一集若沿用旧 `magic-words` 身份，在迁移日映射旧阅读完成记录。旧版当天已领的故事 +2 应抵扣新任务的目标额度，最多补差到 5，不再完整发 5。旧记录若不能确定对应故事，当天保守关闭重复来源；第二天按新规则正常开始。
- 完成记录、已领取键、余额与每日上限在同一次存档提交中写入。先持久化成功，再表现积分到账。失败保留待恢复状态，重试不能重发。

## 9. 动画资产与内容生产

### 统一制作方法

1. 写明单集的情感变化、生活行动、语言目标及可选参与点。
2. 审阅故事稿和分镜，形成固定角色参考：外形、比例、表情、材质、光线、道具尺寸。推荐先试温暖黏土绘本风；这仍是样片方案。
3. 用 GPT Image 2.6 制作角色、关键画面和短动作。角色动作逐姿态生成，每个独立帧只承载一个姿态，随后合成；可测试原生 GIF，但需确认实际输出和权限。
4. 动作按镜头需要制作：呼吸、眨眼可循环；倒水、递苹果、咬一口是一次性动作，不能无休止重复。
5. 先用临时声音核对节奏；脚本与样片通过后制作正式配音。英语发音、语气和停顿与画面一起审校，不让长旁白压过角色表演。
6. 输出可控播放的短片或序列帧、静态关键帧、旁白、字幕和时间轴。GIF 可以是制作中间物，不必直接作为网页最终载体。
7. 逐镜检查角色一致性、物体接触、道具数量、光线、镜头衔接、声音和动作同步；再检查整集与交互分支。

首集素材清单：2 份角色参考包、果园/野餐区/洗果近景的场景参考、8 个叙事段落所需的短镜头、2 个参与入口与对应动作、接物/吃点心/感谢/告别等可复用短动作，以及旁白与静态兜底图。实际出图数量需通过试制确认，不将段落数或镜头数等同于调用次数。

### 全部核心交互动画化如何扩展

角色收集范围与已制作动画范围分开管理。首批以少数角色验证所有核心动作，再逐批覆盖其余伙伴；不让宝宝已拥有的角色因缺新动画而消失。

| 资产层 | 用途 | 规模控制 |
|---|---|---|
| 固定故事演员 | 完整生活故事与情绪表演 | 每集少数固定演员，不生成任意双角色组合 |
| 个人伙伴短动作 | 招手、接食物、玩球、休息、回家 | 每个角色建立能力清单，优先高频伙伴，再补齐收藏角色 |
| 共用环境与道具 | 果园、菜园、座位、球、水壶、天气 | 布局与灯光统一，按镜头复用 |
| 收藏与捕捉镜头 | 自由选喜欢的角色，投球、入球、回家 | 共用镜头编排；角色自身动作仍需独立验收 |

例如 6 个试点角色 × 5 个基础动作就是 30 组角色动作包；388 个角色全部覆盖同样动作将是 1,940 组。这是范围算术，不是生成次数或成本估计。共用道具、镜头与合成能减少重复工作，但不能靠替换名字或贴头像保证角色动作正确。

迁移期未具备新动作的角色继续使用现有陪伴路径，清楚保留在试点之外；不能将这种混合状态宣称为“全量动画化完成”。最终完成标准是所有保留的核心互动都有可验证的动作表现及可用兜底。还没有具体报价或工期，先用一集测得返工率、文件体积和制作时间。

### 内容契约

每集至少包含：`episodeId`、稳定 `taskId`、`contentVersion`、演员、主题、语言目标、镜头顺序、旁白、媒体/静态兜底、自然继续路径、可选动作、需要的状态条件、效果事件及结尾。播放进度另存 `shotId`、位置和已完成镜头，奖励身份与素材版本分离。

每个可选动作必须有三条清楚的路径：主动参与、没有参与、被暂停或打断。自动继续不等于自动消费，不得在无人操作时购买精灵球、选择新伙伴、消耗已有食物或改动真实农田库存。故事内角色自有道具可自然使用。

### 播放与事务规则

- 状态至少区分 `loading / playing / invitation / paused / committing / completed / recovery`。不要只用互相独立的定时器控制声音、画面和奖励。
- 下一镜头基于当前媒体/旁白实际完成；加载失败、后台挂起和重复回调不能直接完成任务。
- 全集有效镜头完成后才结算；跳页或直接跳结尾不自动补全。静音模式可记录观看，不记录“听过”；有家长共读兜底时另记其来源。
- 每个改变库存或伙伴状态的事件有稳定 `eventId`，持久化已应用事件。手势与自动继续同时发生时只执行一条路径。
- 重播只重播演出，不重复扣食物、加友好度、收获或加积分。请求成功前不展示不可逆的成功结尾；存档失败从已有快照恢复。
- 兑换、捕捉沿用 [pokeballs.ts](../../../src/lib/pokeballs.ts) 与 `store.ts` 的提交约束；动画与存档不能各自成功、互相脱节。
- 到时立即进入既有休息机制并保存镜头位置，不能为了播完故事绕过家长时长设置。下次从恰当的语句/镜头起点续接。
- 只预取当前集的开场与相邻镜头，不在首页一次加载全部故事。首版媒体预算在试制后定；无网只承诺已经缓存的内容。
- 动态素材不可用时使用已验收的关键帧与可用声音，保留暂停、返回和恢复。声音也不可用时，不对不识字宝宝偷偷切到文字播放并计作学习完成。
- `prefers-reduced-motion` 使用稳定关键帧与旁白；避免持续镜头抖动、强闪烁、过快推拉。

### 技术验证范围

需要用有意义的状态测试覆盖：完成去重、同日跨语言/版本去重、每日额度、新旧奖励混合及先后顺序、旧故事 +2 抵扣与旧三类 +1 的组合、旧存档迁移、兑换/捕捉失败恢复、后台暂停、手势与自动继续竞争。浏览器覆盖鼠标与触控、横竖屏、静音和弱网。只在正式实现后运行完整 `npm run check` 与网页构建；本轮文档研究不代表这些检查通过。

## 11. 分阶段交付与验收

| 阶段 | 交付对象 | 完成判据 |
|---|---|---|
| A · 研究与规格 | 本文、一页概览、首集文字分镜 | 已完成本轮资料与源码核查；视觉和时长仍待样片 |

| C · 收集闭环与三个场景 | 故事任务、兑换、捕捉、回家；点心/种植/游戏各一集及实际伙伴互动 | 新旧存档可用，奖励与消费不重复；喂已拥有伙伴的库存扣除与吃饱反馈、真实农田状态、游戏互动分别验收 |
| D · 扩展与替换主入口 | 角色动作库、更多故事、旧功能迁移 | 按角色与行为能力表验收，未覆盖项明确；再进行网页发布与线上回读 |

先把一集从开始到收尾做完整，然后接入收集闭环。工程骨架和内容制作可并行；正式批量素材制作以前，审阅的是具体角色参考、关键镜头与约 20–30 秒动作样片，不需要再批准一份抽象计划。

### 样板验收目标（尚未实测）

| 项目 | 目标 | 证据 |
|---|---|---|
| 故事启动 | 从主画面一次明确点击开始 | 浏览器操作记录与声音解锁结果 |
| 额外操作 | 开始后零强制答题/翻页；最多两次可选参与 | 全程不操作和主动参与两条路径 |
| 情境理解 | 家长能描述孩子从画面看懂的行为，记录需要解释的地方 | 少量家庭观察；不以一次观察证明教学效果 |
